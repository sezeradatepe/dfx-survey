01 · Giriş

API First Nedir?

Bir API, iki yazılımın birbiriyle nasıl konuşacağını tanımlayan sözleşmedir. API First yaklaşımında bu sözleşme projenin ilk çıktısıdır: önce API tasarlanır, gözden geçirilir ve onaylanır; backend, frontend, mobil ve test ekipleri işlerini bu sözleşmeye göre yapar.

🏗️
Mimari proje benzetmesi

Bir bina inşa edilirken önce mimari proje çizilir. Elektrikçi, tesisatçı ve marangoz aynı projeye bakarak aynı anda çalışabilir. Projesiz başlanan binada her usta bir öncekinin işini bekler, duvarlar sonradan kırılır. OpenAPI dokümanı, yazılımın mimari projesidir.

Önce kod yazılır, API onun yan ürünü olarak ortaya çıkar. Controller'lar yazılır, Swagger dokümanı koddan üretilir ve frontend ekibi bu dokümanı ancak backend bittikten sonra görür.

Sorun: API'nin şekli, backend'in iç yapısını (entity'ler, tablo isimleri) yansıtır. Tüketiciler tasarıma dahil edilmez ve hatalar geç fark edilir.

Önce sözleşme yazılır (genellikle OpenAPI/YAML). Sözleşme tüm paydaşlarla gözden geçirilir; mock sunucu ayağa kaldırılır; ardından ekipler paralel çalışır. Kod, sözleşmeye uymak zorundadır.

Kazanç: API, onu kullanacak kişinin ihtiyacına göre şekillenir. Yanlış anlaşılmalar kod yazılmadan, birkaç satır YAML değiştirerek düzeltilir.

⚠️
API First ≠ "Swagger kullanmak"

Koddan otomatik Swagger üretmek dokümantasyondur, API First değildir. API First'ü belirleyen şey sıralamadır: sözleşme koddan önce gelir ve kod sözleşmeye uyar, tersi olmaz.

02 · Temel öncelik

Neden API First?

API First'ün asıl değeri, ekiplerin aynı şeyi anlamasını ve birbirini beklememesini sağlamasıdır. Aşağıdaki faydaların hepsi bu iki fikirden doğar.

⚡

1. Paralel geliştirme

Sözleşme onaylandığı anda backend, frontend, mobil ve QA aynı anda başlar. Frontend gerçek backend yerine sözleşmeden üretilen mock sunucuya bağlanır. Teslim süresi ciddi oranda kısalır.

📜

2. Tek doğru kaynak

"Bu alan zorunlu muydu?", "Tarih hangi formatta?" sorularının cevabı tek bir yerdedir: OpenAPI dosyası. Wiki, e-posta, Slack mesajı arasında kaybolan bilgi kalmaz.

🔍

3. Erken geri bildirim

Tasarım hataları kod yazılmadan, review sırasında yakalanır. YAML'da bir alanın adını değiştirmek dakikalar sürer; canlıdaki bir API'de değiştirmek haftalar sürer.

👥

4. Tüketici odaklı tasarım

API, veritabanı tablolarının aynası olmak yerine onu kullanacak ekranın ve senaryonun ihtiyacına göre şekillenir. Tüketici tasarım masasına baştan oturur.

🤖

5. Otomasyon

Tek bir sözleşmeden server stub'ları, istemci SDK'ları (TypeScript, Kotlin, Swift…), mock sunucular, dokümantasyon ve test senaryoları otomatik üretilir. Elle yazılan tekrar eden kod azalır.

🧪

6. Test edilebilirlik

Sözleşme, testin beklenen sonucudur. Contract testleri, kodun sözleşmeden saptığını CI'da otomatik yakalar. QA, test senaryolarını backend bitmeden yazmaya başlar.

📏

7. Tutarlılık ve yönetişim

Tüm API'ler aynı kurallara (isimlendirme, hata formatı, sayfalama) uyar. Linter araçları (ör. Spectral) bu kuralları otomatik denetler. Bir API'yi öğrenen, hepsini öğrenmiş olur.

🚀

8. Hızlı onboarding ve entegrasyon

Yeni katılan bir developer veya dış iş ortağı, kodu okumadan API'yi sözleşmeden anlar ve Swagger UI'da dener. Entegrasyon süresi günlerden saatlere iner.

Bir senaryo: kitap detay ekranı

  1. Backend 2 hafta boyunca kitap detay endpoint'ini geliştirir; frontend bekler.
  2. Frontend entegrasyona başlar: kitabın müsait olup olmadığı dönmüyor, ödünç geçmişi ayrı bir istekte geliyor.
  3. Ekran tasarımı tek istekte her şeyi bekliyordu. Backend yeniden düzenlenir: +1 hafta.
  4. Bu arada mobil ekip eski yapıya göre geliştirme yapmıştı; onlar da yeniden yazar.
  1. 1. gün: Backend, frontend ve PO birlikte GET /books/{id} sözleşmesini yazar.
  2. Review'da frontend "müsaitlik durumu da dönsün, son ödünç kayıtları aynı yanıtta gelsin" der. YAML'da 5 dakikada güncellenir.
  3. 2. gün: Mock sunucu ayakta. Frontend ve mobil ekranları geliştirir, backend gerçek implementasyonu yazar.
  4. Entegrasyon günü sürpriz yoktur; contract testleri zaten yeşildir.
💡
Özetle

API First, işi yavaşlatan bir "dokümantasyon zorunluluğu" değildir. Başta harcanan küçük bir tasarım zamanı, sonradan yaşanacak büyük yeniden yazma maliyetini ortadan kaldırır.

03 · Neden erken?

Değişikliğin Maliyeti

Bir API'de aynı değişikliği (örneğin bir alanın adını değiştirmek) ne kadar geç yaparsanız o kadar pahalıya mal olur. API First, değişikliği grafiğin en ucuz noktasına çeker.

Değerler temsilidir; amaç büyüklük sırasını göstermektir.

🔗
Canlıdaki API neden bu kadar pahalı?

Yayındaki bir API'yi değiştirdiğinizde sadece kendi kodunuzu değil, onu kullanan herkesin kodunu etkilersiniz: web, iOS, Android, iş ortakları. Mobil uygulamaların eski sürümleri aylarca kullanılmaya devam eder. Bu yüzden canlıdaki bir API'yi değiştirmenin kurallarını Versiyonlama Düsturu bölümünde ayrıca ele alıyoruz.

05 · Sözleşme

Sözleşme: OpenAPI

REST API'ler için endüstri standardı OpenAPI Specification'dır (eski adıyla Swagger). Sözleşme, insanların okuyabildiği ve makinelerin işleyebildiği bir YAML veya JSON dosyasıdır.

src/main/resources/openapi/library-api.yamlyaml
openapi: 3.0.3
info:
  title: Library API
  version: 1.0.0
paths:
  /api/v1/books/{bookId}/loans:
    post:
      summary: Bir kitabı ödünç alır
      operationId: borrowBook
      tags: [Loans]
      parameters:
        - name: bookId
          in: path
          required: true
          schema: { type: integer, format: int64 }
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/LoanRequest' }
      responses:
        '201': { description: Ödünç kaydı oluşturuldu }
        '404': { $ref: '#/components/responses/NotFound' }
        '409': { description: Kitap şu anda başka bir üyede }
components:
  schemas:
    LoanRequest:
      type: object
      required: [memberId]
      properties:
        memberId:
          type: integer
          format: int64
        dueDate:
          type: string
          format: date

📖 Dokümantasyon

Swagger UI / Redoc ile okunabilir ve denenebilir doküman.

🎭 Mock sunucu

Prism, WireMock gibi araçlar sözleşmeden sahte bir API ayağa kaldırır. Frontend ilk günden çalışır.

⚙️ Kod üretimi

💡
Spring Boot'ta API First

openapi-generator ile interfaceOnly modunda bir BooksApi arayüzü üretilir; controller bu arayüzü implements eder. Sözleşmede bir alan değişirse proje derlenmez. Böylece kod ile sözleşmenin ayrışması derleme hatasına dönüşür.

06 · Kurallar

API Tasarım Kuralları

Sözleşmeyi yazmak yeterli değildir; iyi bir sözleşme öngörülebilir olmalıdır. Aşağıdaki kurallar tüm API'lerimizin aynı dili konuşmasını sağlar.

Kaynak ve URL kuralları

1. URL'ler isim (kaynak) içerir, fiil içermez

YanlışPOST /createBook
GET /getBookById?id=7
DoğruPOST /books
GET /books/7

2. Koleksiyonlar çoğul isimle adlandırılır

Yanlış/book/7 · /bookList
Doğru/books · /books/7

3. URL'ler küçük harf ve kebab-case; JSON alanları camelCase

Yanlış/Book_Authors · {"Book_Id": 7}
Doğru/book-authors · {"bookId": 7}

4. İlişkiler hiyerarşiyle gösterilir, en fazla 2 seviye

Yanlış/libraries/3/shelves/2/books/7/loans
Doğru/books/7/loans · /members/5/loans

HTTP metotları

5. Her metot tek bir anlam taşır ve bu anlam her API'de aynıdır.

MetotAnlamıÖrnekIdempotent?

🔁
Idempotent ne demek?

Aynı isteği 1 kez de 10 kez de göndersen sonuç aynıdır. Ağ hatasında istemci isteği güvenle tekrar edebilir. POST idempotent değildir; tekrarlanırsa iki kayıt oluşabilir. Ödeme gibi kritik işlemlerde Idempotency-Key başlığı kullanılır.

HTTP durum kodları

6. Durum kodu, yanıtın gövdesine bakmadan ne olduğunu anlatmalıdır. Hata durumunda asla 200 OK dönülmez.

Veri ve davranış kuralları

7. Entity değil, DTO dön

Veritabanı yapısı API'ye sızmamalıdır. Tabloya kolon eklemek API'yi değiştirmemelidir. Ayrıca entity dönmek, şifre gibi alanların yanlışlıkla ifşa edilmesine yol açabilir.

8. Tarih ISO 8601, para birimiyle

"2026-11-01T10:30:00Z" gibi saat dilimli tarih kullanın. Tutarlar {"amount": "12.50", "currency": "TRY"} biçiminde verilir.

9. Listeler sayfalanır

GET /books?page=0&size=20. Yanıt toplam kayıt bilgisini de içerir. Sınırsız liste dönen endpoint, veri büyüdüğünde sistemi yavaşlatır.

10. Filtre ve sıralama query parametresidir

GET /books?status=AVAILABLE&sort=title,asc. Durum filtrelemek için yeni bir URL (/books/available) açmak yerine parametre kullanılır.

11. Enum değerleri belgelenir

Alabileceği değerler sözleşmede enum: [AVAILABLE, ON_LOAN] olarak yazılır. İstemciler, ileride yeni değer eklenebileceğini varsayarak bilinmeyen değerleri tolere etmelidir.

12. Güvenlik sözleşmenin parçasıdır

Hangi endpoint'in hangi rolü istediği securitySchemes ile sözleşmede tanımlanır. Token, şifre gibi hassas bilgiler URL'de taşınmaz.

07 · Kurallar

Hata Yanıtları

Başarılı yanıtlar kadar hata yanıtları da sözleşmenin parçasıdır. Tüm API'ler aynı hata formatını kullanmalıdır. Önerilen standart RFC 9457 – Problem Details'tir ve Spring'de ProblemDetail sınıfı ile hazır gelir.

Yanlış HTTP 400
"Kitap zaten ödünç verilmiş"
Düz metin; istemci bunu programatik olarak ayırt edemez, durum kodu da yanlış.
Doğru HTTP 409 · application/problem+json
Makinenin okuyabileceği bir hata tipi, insanın okuyabileceği bir açıklama ve doğru durum kodu.
HTTP/1.1 409 Conflictjson
{
  "type": "https://api.example.com/problems/book-not-available",
  "title": "Kitap müsait değil",
  "status": 409,
  "detail": "Bu kitap şu anda başka bir üyede ödünçte.",
  "instance": "/api/v1/books/7/loans",
  "errorCode": "BOOK_NOT_AVAILABLE"
}
🔒
Hata yanıtına neler konmaz?

Stack trace, SQL sorgusu, sınıf adı, sunucu yolu. e.getMessage() değerini doğrudan istemciye dönmek, saldırgana sistemin iç yapısı hakkında bilgi verir.

08 · Kurallar

Versiyonlama Düsturu

Bir API yayınlandığı anda bir söz verilmiş olur. Versiyonlama, bu sözü bozmadan API'yi geliştirmenin yoludur. Altın kural tek cümledir:

🥇
Ekle, değiştirme. Değiştirmen gerekiyorsa yeni versiyon aç.

Mevcut tüketiciyi bozmayan her değişiklik aynı versiyonda yapılır. Mevcut tüketiciyi bozan her değişiklik yeni bir ana versiyon (v2) gerektirir.

Kırıcı (breaking) ve kırıcı olmayan değişiklikler

✅ Kırıcı değil – aynı versiyon

  • Yanıta yeni bir alan eklemek
  • Yeni bir endpoint eklemek
  • İsteğe opsiyonel bir alan veya parametre eklemek
  • Bir doğrulamayı gevşetmek (ör. max uzunluğu artırmak)
  • Dokümantasyonu iyileştirmek

❌ Kırıcı – yeni ana versiyon

  • Bir alanı silmek veya adını değiştirmek
  • Bir alanın tipini değiştirmek (id: number → string)
  • Opsiyonel alanı zorunlu yapmak
  • URL'i veya HTTP metodunu değiştirmek
  • Durum kodunun veya hata formatının anlamını değiştirmek

Kendini dene: kırıcı mı, değil mi?

Versiyon nereye yazılır?

YöntemÖrnekArtıEksi

Düsturumuz

1️⃣

Sadece ana versiyon URL'de

URL'de yalnızca v1, v2 yer alır. v1.2.3 gibi ara sürümler URL'ye yazılmaz; sözleşmenin info.version alanında semantik versiyon olarak tutulur.

2️⃣

İlk günden v1

"Henüz değişmez" diye versiyonsuz başlanmaz. Sonradan versiyon eklemek başlı başına kırıcı bir değişikliktir.

3️⃣

Aynı anda en fazla 2 versiyon

Her versiyon bakım yükü demektir. Yeni versiyon yayınlandığında eskisi için bir kapanış takvimi açıklanır.

4️⃣

Önce duyur, sonra kapat

Eski versiyonun yanıtlarına Deprecation ve Sunset başlıkları eklenir. Tüketicilere geçiş rehberi verilir. Hiçbir versiyon habersiz kapatılmaz.

5️⃣

İstemciler toleranslı okur

İstemci, tanımadığı yeni alanları görmezden gelmelidir. Böylece alan eklemek her zaman güvenli kalır (Tolerant Reader).

6️⃣

Kırıcı değişiklik CI'da yakalanır

openapi-diff gibi araçlar yeni sözleşmeyi eskisiyle karşılaştırır. Kırıcı bir fark varsa ve versiyon artırılmamışsa build kırılır.

Kapanması planlanan v1 yanıtıhttp
HTTP/1.1 200 OK
Deprecation: @1772323200
Sunset: Tue, 30 Jun 2027 23:59:59 GMT
Link: </api/v2/books>; rel="successor-version"

Deprecation başlığı (RFC 9745) API'nin kullanımdan kaldırıldığı anı, Sunset başlığı (RFC 8594) ise tamamen kapatılacağı tarihi bildirir.

10 · Pekiştirme

Sık Sorulanlar

API First işi yavaşlatmaz mı?
İlk gün yavaşlatıyor gibi görünür, çünkü kod yazmadan önce tasarıma zaman ayrılır. Ancak paralel geliştirme ve entegrasyonda yaşanmayan sürprizler sayesinde toplam teslim süresi kısalır. "Değişikliğin Maliyeti" grafiğini hatırlayın.
Tek başıma geliştirdiğim küçük bir projede de gerekli mi?
Zorunlu değildir. API First'ün faydası API'nin tüketici sayısı ve ömrü arttıkça büyür. Yine de birkaç endpoint'lik bir projede bile önce sözleşmeyi düşünmek tasarımı iyileştirir.
Sözleşme değişirse ne olur?
Sözleşme de kod gibi Git'te versiyonlanır ve pull request ile değiştirilir. Değişiklik kırıcı değilse aynı versiyonda devam edilir; kırıcıysa yeni ana versiyon açılır.
Koddan Swagger üreten bir araç (ör. springdoc) kullanmak API First sayılır mı?
Hayır. springdoc koddan doküman üretir; bu code first'tür. API First'e geçmek için sözleşme dosyası kaynak olarak tutulur ve kod (ör. openapi-generator ile) ondan türetilir. springdoc yine de Swagger UI sunmak için kullanılabilir.
Neden v1.1 değil de sadece v1?
Kırıcı olmayan değişiklikler mevcut tüketiciyi etkilemez, bu yüzden tüketicinin URL değiştirmesine gerek yoktur. URL'deki versiyon yalnızca "bu sözleşme bozuldu, yenisine geçmen gerek" mesajını taşır.
